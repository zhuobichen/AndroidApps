# videoquiz-paper：卷灵读卷与作答

你是这条流水线上的执行者。用户从手机拍了试卷传上来，你要给出**题号完整、可复核**的答案。

**核心信条：拿不准就说拿不准，绝不臆造。** 这条比"给出答案"更重要——
用户已经验证过：如实报告"这一段没有题目"，比硬凑一个答案有价值得多。

## 1. 读卷：用流水线，不要重写脚本

**这是本技能存在的意义。** 以前每个任务都重写 20 个脚本、反复试参数，
现在固化成一条命令：

```powershell
cd D:\Android\MapMate\VideoQuiz\bridge
python pipeline.py run --job <任务目录>
```

大约 90 秒~5 分钟跑完，产出 `<job>/work/questions_draft.json`。

也可以分阶段跑（某一步失败时只重跑那一步，中间产物会复用）：

```powershell
python pipeline.py probe   --job <job>          # 先看视频性质
python pipeline.py frames  --job <job> --step 10
python pipeline.py dedup   --job <job>
python pipeline.py rectify --job <job>
python pipeline.py ocr     --job <job>          # 自动发现 OCR 端口
python pipeline.py stitch  --job <job>
python pipeline.py parse   --job <job>
python pipeline.py gap     --job <job> --ranges "[[840,870,2]]"   # 对特定帧加密回补
```

### 每个阶段看什么指标

流水线会打印 `PIPELINE {...}` 行，**必须读这些数**，不能只看"跑完了"：

| 阶段 | 正常值 | 越界怎么办 |
| --- | --- | --- |
| probe | `guess_profile: handheld` + `bright_ratio > 0.2` | 纯录屏会是 `dark/mixed`，可跳过透视校正 |
| dedup | `ratio` 10%–80% | **低于 10% 说明去重失效**（手持滚动），改逐帧全留 |
| rectify | `ratio > 0.6` | 低于说明拍太斜/纯录屏，OCR 改读 `frames` |
| ocr | `per_frame_s < 1.0` = 真 CUDA | **>1.0s 说明退到 CPU**，去查 OCR 服务 |
| stitch | `moved_pairs` 接近帧数 | 大部分为 0 说明没滚动，可能只拍了一屏 |
| parse | 题号连续、`incomplete` 少 | 见下方红线 |

### 质量红线（硬性）

1. **题号必须是连续的 1..N**。有缺号就说明漏题，必须用 `gap` 回补或说明原因。
2. **题号不能是 0，也不能超出现实范围**。曾出现 `D. 在治理中保护…` 被误拆成 0 号题的事故，
   已在 `QRE` 里用 `[1-9]\d{0,2}` 约束；如果你发现异常编号，先怀疑解析而不是视频。
3. **同一题号跨页串号**：视频里不同页可能出现相同编号（分区各自从 1 开始）。
   流水线会检测并标 `跨页串号`，这类要人工判断是不是同一道题。
4. **选项不全时不许猜**。`incomplete=true` 的题，要么回补，要么在结果里写明"只拍到 N 个选项"。

## 2. 读卷之后的核对（不能省）

流水线给的是**草稿**，你必须核对：

1. **看长图**：`work/panorama.png` + `work/slices/slice_*.png`（每片 2200 高）。
   逐片扫一眼，确认没有大片空白、没有重复页、没有接错位置。
2. **对题号**：草稿里 `1..N` 是否连续？分区标题（如"单选题-企业文化"）是否都在？
3. **挑可疑**：`lowConfidence` 列表里的、`incomplete` 的，优先回看原图。

OCR 常见错字（本机实测过的）：

```
三峨/三映 → 三峡        两算 → 两翼
破中和 → 碳中和         胡梦卜素 → 胡萝卜素
```

这类同音/形近错字，**按图修正**，并在 notes 里记一句改了什么。

## 3. 答题：判定模型 + 自解

如果环境有 `task.ps1`：

```powershell
& "<job 上级>\task.ps1" -Operation ask-jev -BaseUrl "<completionUrl>" -Id "<id>"
```

返回：
- `answered`：判定模型有把握的（**直接采用，不要重新推理**）
- `unresolved`：它也没把握的，你自己解
- `skippedFigure`：图形题被跳过，你自己解

**分工原则**（实测有效）：
- 确定性选择题（文学常识、时政、简单计算）→ 判定模型
- 需要推理/计算/主观表述的 → 自己解
- 依赖图形/图表的 → 自己解，并在 notes 说明图像情况

例：三峡 60 题，判定模型 16 题，自解 44 题。

---

## 4. 联网核实的边界

**允许联网搜索**，但要守规矩：

- **值得查**：成语典故出处、文言实词义项、时政事件、专有名词（企业口号/价值观）、翻译选词、公式常数
- **查了要写明来源**：`detail` 里写"据 XX 官网/词典"，`notes` 里说明哪题是这样定的
- **不许拿搜索来的"参考答案"直接抄**——如果你在某个网站看到"本卷第 5 题选 B"，
  那可能是错答案。要**核对事实**（比如企业官网原文），不是核对别人给的答案

实测案例：三峡第 2 题原判 B，查官网发现"舍家为国、无私奉献"对应的是**奋斗精神**，
选项写"奉献精神"才是错的 → 改判 D。这是核对事实，不是抄答案。

## 5. 输出格式

写到 `<job>/results/answers.txt`，**纯文本**：

```
<试卷名称>（共 N 题）作答结果

==================== 结果摘要 ====================
1. 判定模型覆盖 X 题：<题号列表>
2. 我自己解 Y 题：<题号列表>，其中 Z 题用穷举/枚举验证
3. 全卷 N 题答案均已确定，其中第 a、b 题在复做中改判（见"改判记录"）
4. 真正仍存不确定性的有 M 题（见"不确定项"）
5. 题目原文经 <帧数> 帧 OCR、跨帧投票与 <切片数> 张整页裁图核对得到

==================== 逐题答案 ====================
【题型-分区（共X题）】
1. B —— 一句话依据
2. D —— 一句话依据

==================== 改判记录（已确认） ====================
- 第 2 题：B → D。原判断错在…，查官网确认…

==================== 不确定项 ====================
- 第 41 题（A、D）：属"多选尺度"判断。若评分规则认为…则只取 D
```

**四条格式要求**：

1. **结果摘要第一条**：判定模型多少题、自己多少题。用户要能一眼看出可靠性。
2. **每题一句话依据**：计算题给算式，文本题给定位（"文中只说…未说…"）。
3. **把「改判」和「不确定」分开**。这两类性质不同，混在一起会让用户以为还有一堆不可靠。
4. **不确定项写清楚"为什么不确定"以及"如果标准不同会变成什么"**。

**默认只出 txt，不要生成 PDF。** 只有用户当次明确说"要 PDF"才做。

## 6. 必须如实说的三种情况

### 6.1 没有题目

拍到了封面、正文、表情包、电脑屏幕……都不是题目。

正确做法：
```
本段为封面及正文，无题号选项，未解出题目。
题干与选项待后续分段补齐，不臆造答案。
```

### 6.2 只拍到一部分

```
第 17 题只拍到末两句，题干在第 3 页未出现在本段，无法独立求解，
故本次不作答第 17 题，需第 3 页的照片补全。
```

### 6.3 选项不全

```
选项只拍到三个，未见 D 项。若原题还有 D 项，请以原卷为准；
本次按可见顺序 C = "成长的衡量"。
```

**这三种情况宁可不答，也不要编。** 用户的实际反馈是：这样处理是对的。

## 7. 分段模式（同一套卷多次提交）

用户可能分多次传同一套卷的不同部分。这时：

- **必须看 `priorAnswers`**：已定稿的题不要重新识别，不要改答案
- **只处理本段新出现的题**，增量追加
- **跨段题**（上一段题干、这一段选项）以本段为准补齐
- 如果本段原文更清晰、与已出答案冲突，**以本段为准**，并在 notes 写明改了哪题、为什么

实测：语文卷 6 段串行，22 题零重复，13/13 选择全对，比整卷模式快 4.6 倍。

## 8. 排障

### OCR 服务找不到

```powershell
# 自动探测 8766-8770；若都没有：
foreach ($p in 8766,8767,8768,8769,8770) {
  try { (Invoke-RestMethod "http://127.0.0.1:$p/health" -TimeoutSec 2) | ConvertTo-Json -Compress } catch {}
}
```

**注意**：端口"能连上"不等于"是 OCR 服务"。本机 8766 曾被别的程序长期占用，
连接成功但 `/health` 返回 404 —— 所以 `discover_ocr_server()` 必须验证返回里有
`engine` 或 `ready` 字段，不能只看端口是否监听。

### OCR 很慢（每帧 > 1 秒）

说明退到 CPU 了。检查：
- `health` 里 `engine` 是不是 `cuda`
- CUDA 依赖 DLL 是否齐全（`cufft64_11.dll`、`cudart64_12.dll`）

### 去重后只剩几帧

手持滚动视频的纵向位移不规律，位移去重会失效（曾有 2222 帧去重成 2 帧）。
流水线会在 `ratio < 10%` 时报警——**看到这个警告就改逐帧全留**，
靠 OCR 文本去重而不是像素位移。

### 视频很长但只拍到 1 题

先 `probe` 看时长。7.5 秒 226 帧却标称 15 题，那就是只拍到了 1 题，
如实报告"视频中共拍到题目数量：1 题"，不要按标称题数编造。

1. 确认 `results/answers.txt` 已写出且非空
2. 跑 `task.ps1 -Operation complete` 上报（如果环境有）

## 附：这套流程的来历

这些规则都来自实际踩过的坑，不是凭空设计的：

| 规则 | 来自哪次事故 |
| --- | --- |
| 去重保留率红线 | 2222 帧位移去重成 2 帧，节目全丢 |
| OCR 端口自动探测 | 8766 被别的服务占用，OCR 静默失败 |

| 跨页串号检测 | 同编号在不同页出现，内容混在一起 |

| 改判与不确定分开 | 用户反馈混在一起会误判可靠性 |
| 默认只出 txt | 用户明确要求的（PDF 改为按需） |
